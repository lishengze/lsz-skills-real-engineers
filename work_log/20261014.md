## 任务：排查并解决 UniCloud Workspace 在 Ubuntu 24.04 上登录即崩溃、无法显示的问题
**时间**：12:40-12:55

### 工作内容
1. **现象**：本机 Ubuntu 24.04.5 登录 Workspace 后报错、无法显示（连接成功但很快断开）。与 22.04 黑屏不同，本机是**崩溃**。
2. **定位崩溃**：
   - 日志确认连接流程正常（grpc 成功、认证成功），但 VdSession 在 SPICE websocket 连接线程崩溃。
   - 4 个 minidump 均为 **SIGSEGV @ 0x0**（异常码 0xb），崩溃线程是 SPICE 主通道连接线程。
   - 协议日志：崩溃发生在 `spice_channel_connect_ws` 发起 `wss://` WebSocket 连接之后。
3. **根因**：
   - Workspace 捆绑的 `libgnutls.so.30` 是 **GnuTLS 3.5.18**（很老），只提供 `GNUTLS_3_4` 符号。
   - 系统 glib-networking 的 `libgiognutls.so` 需要 `GNUTLS_3_6_3`/`GNUTLS_3_7_4` 符号。
   - start.sh 把 RUN 目录放 LD_LIBRARY_PATH 首位，导致 `libgiognutls.so` 加载了捆绑的旧 GnuTLS → 缺符号 → wss TLS 连接空指针崩溃。
   - 22.04 正常是因为其 glib-networking 只需旧 GnuTLS 符号；24.04 需 3.7.4+，故崩溃。
4. **修复**：重命名捆绑的 `libgnutls.so.30` → `.bak`（连同 `libgnutls.so.30.14.10`），强制加载器回退到系统 GnuTLS 3.8.3。
5. **验证**：重命名后 `libspice-client-glib-2.0.so` 与 `libgiognutls.so` 均解析到系统 `/lib/x86_64-linux-gnu/libgnutls.so.30`，无缺失符号；spice 客户端仅需 `gnutls_add_extension_string`，系统 3.8.3 完全满足。重启 Workspace，登录界面正常。

### 结论
- **根因 = 捆绑的旧 GnuTLS 3.5.18 与 Ubuntu 24.04 的 glib-networking 不兼容**（缺 GNUTLS_3_7_4 符号），导致 SPICE wss:// TLS 连接崩溃。
- 修复 = 让系统 GnuTLS 3.8.3 替代捆绑旧版（重命名捆绑库，备份为 .bak）。
- 附带发现：VdSession 还会报 camrdr 摄像头重定向 init 失败（rc=17），属独立问题，不影响显示。

### 经验教训
1. **Workspace 在 24.04 崩溃≠22.04 黑屏**：先看崩溃转储/日志判定是崩溃还是黑屏，再对症下药，不要照搬 22.04 的 GStreamer 修复。
2. **捆绑旧库与系统库版本符号冲突**是升级系统后高频崩溃源：`ldd <so>` 出现 `version 'XXX' not found`，说明运行时 LD_LIBRARY_PATH 优先加载了捆绑旧库。用 `readelf -V` 对比捆绑库与系统库的版本符号。
3. **排查崩溃优先看 minidump 异常码**：SIGSEGV(0xb)@0x0 = 空指针解引用，结合协议日志定位到具体连接线程。
4. **修复方式**：重命名捆绑的冲突库（备份 .bak）强制用系统库，比改 LD_LIBRARY_PATH 顺序更精准、副作用小。
5. **跨版本适配**：同一客户端在 22.04 正常、24.04 崩溃，优先检查捆绑的第三方库（openssl/gnutls/glib）与新版系统库的符号兼容。

## 任务：Workspace 24.04 修复补充——libgnutls 重命名不够，需 LD_PRELOAD shim 补齐 H3C 定制符号
**时间**：13:00-13:15

### 工作内容
1. **反馈**：用户重连后仍失败。确认 libgnutls 重命名已解决 SIGSEGV（无新 minidump，SPICE websocket 连接成功），但 VdSession 进程在 `vdpCore connect success` 后退出（无 minidump）。
2. **定位**：`/tmp/ws_restart.log`（start.sh 后台输出）捕获到 VdSession stderr：`undefined symbol: gnutls_add_extension_string, version GNUTLS_3_4`。
3. **根因深化**：两个 GnuTLS 各缺对方所需符号——
   - 捆绑 GnuTLS 3.5.18：有 H3C 定制 `gnutls_add_extension_string@GNUTLS_3_4`（spice 需要），缺 GNUTLS_3_6_3/3_7_4（libgiognutls 需要）
   - 系统 GnuTLS 3.8.3：有 GNUTLS_3_7_4（libgiognutls 需要），缺 H3C 定制符号（spice 需要）
4. **解决**：编译 LD_PRELOAD shim `libgnutls_h3c.so`：
   - 用 `.symver` 以 `GNUTLS_3_4` 非默认版本导出 `gnutls_add_extension_string`
   - 实现内 `dlopen` 捆绑 GnuTLS `.bak` 转发真实函数，失败兜底返回 0
   - start.sh 加 `export LD_PRELOAD=.../libgnutls_h3c.so`
5. **验证**：`.symver` 测试程序调用 `gnutls_add_extension_string@GNUTLS_3_4` 成功返回 0；shim 能 dlopen `.bak` 找到真实实现；Workspace 重启后 LD_PRELOAD 生效，登录界面正常。

### 结论
- **完整修复 = libgnutls 重命名（让系统 GnuTLS 生效，解决 SIGSEGV）+ LD_PRELOAD shim（补齐 H3C 定制符号，解决 symbol lookup error）**。
- 附带：VdSession stderr 在 `/dev/null`，但 start.sh 后台输出会捕获到 `symbol lookup error`，是排查链接错误的关键线索。

### 经验教训
1. **"undefined symbol: xxx, version V" 与 "version 'V' not found" 是两种相反问题**：
   - `version 'V' not found` = 加载了太旧的库，缺新符号（→ 用更新的库）
   - `undefined symbol: xxx, version V` = 加载了太新的库，缺定制旧符号（→ 需补符号）
2. **同一 soname 两个库各缺对方符号**（捆绑旧库 vs 系统新库）时，不能只选一个；用 LD_PRELOAD shim 补齐缺失符号，`.symver` 指定版本 + 转发到另一库实现。
3. **链接错误不是崩溃**：进程无 minidump 直接退出，stderr 报 symbol lookup error。捕获 VdSession stderr 是关键（start.sh 后台输出 `/tmp/ws_restart*.log`）。
4. **H3C 定制函数**（如 `gnutls_add_extension_string`）只存在于捆绑库，系统库不可能有，跨版本适配必须保留定制符号。

## 任务：Workspace 24.04 黑屏——捆绑 GStreamer 1.14 解码链（旧 FFmpeg + libva-x11 符号缺失 + 注册表缓存）
**时间**：14:10-14:40

### 工作内容
1. **反馈**：登录连接成功但仍黑屏；用户提示考虑 Wayland。确认本机是 X11（非 Wayland），排除。
2. **误判排除**：安装系统 gstreamer1.0-plugins-bad/ugly/libav 无效（VdSession 用的是**捆绑 GStreamer 1.14**，非系统）。
3. **定位**：VdSession 日志 `trying avdec_h264... GstPlayerBase::doPipeBuildManual m_decbin create failed, m_src:0x0` → avdec_h264 元素创建失败。
4. **根因链**：捆绑 `libgstlibav.so`（需旧 FFmpeg libavcodec57 等，RUN 目录已有）→ 依赖 `libgstvaapi.so` → 依赖捆绑 `libva-x11.so.2`（需数据符号 `va_fool_postp`）→ 捆绑 `libva.so.2` 核心缺失 → 系统 libva 无此符号 → 插件加载失败 → avdec 不注册 → 黑屏。
5. **修复**：① 禁用捆绑 libva-x11（重命名 .bak，系统 libva-x11 生效）；② 删 GStreamer 注册表缓存强制重扫；③ 重启 Workspace。用 `ctypes.CDLL` 复现插件加载、`gst_element_factory_make` 验证 avdec_h264 创建成功。

### 结论
- 黑屏根因 = 捆绑 GStreamer 1.14 解码链中 libva-x11 缺 `va_fool_postp` + 注册表缓存旧状态。禁用捆绑 libva-x11 + 删缓存解决。
- 与 22.04（系统 GStreamer 缺插件）不同：24.04 VdSession 用捆绑 GStreamer，装系统插件无效。

### 经验教训
1. **先确认用哪套 GStreamer**（GST_PLUGIN_PATH），再决定装系统插件还是修捆绑链。
2. **`undefined symbol` 是数据对象**（objdump -T 显示 DO *UND*）= 缺全局变量/回调，禁用不配套捆绑库比补符号干净。
3. **GStreamer 注册表缓存会缓存加载失败状态**，修复底层后必须删 `~/.cache/gstreamer-1.0/registry.*`。
4. **`ctypes.CDLL(..., RTLD_NOW)` 能直接复现插件加载错误**；用 `env LD_LIBRARY_PATH=...` 而非改 os.environ。
