# 03 工程技能详解（Engineering Skills）

> 每日代码工作技能，位于 `skills/engineering/`，共 20 个（推广）。分 User-invoked 与 Model-invoked 两类。

## 1. User-invoked（人类触发）

| 技能 | 作用 | 触发场景 |
|------|------|---------|
| **ask-matt** | 路由器，问"该用哪个技能/流程" | 不确定当前情况用哪个技能时 |
| **grill-with-docs** | 拷问会话，同时构建领域模型（更新 GLOSSARY.md 和 ADR） | 想深度对齐 + 建立共享语言 |
| **triage** | 让 Issue 走三分类状态机 | 把 Issue 分诊到各 triage role |
| **improve-codebase-architecture** | 扫描代码库找"加深(depening)"机会，输出可视化 HTML 报告，再拷问选定项 | 每隔几天跑一次，防泥球 |
| **setup-matt-pocock-skills** | 为仓库配置工程技能（issue tracker、triage labels、领域文档布局） | 用工程技能前先跑一次 |
| **to-spec** | 把当前对话合成 spec 发布到 issue tracker（不再访谈） | 已讨论清楚，要落成 spec |
| **to-tickets** | 把 plan/spec/对话拆成一组 tracer-bullet tickets，各自声明阻塞边 | 大目标拆解成可执行工单 |
| **implement** | 按 spec/ticket 构建，在预定 seam 驱动 `/tdd`，提交前用 `/code-review` 收尾 | 实现一个 spec/ticket |
| **implement-spec** | 在一条集成分支上实现整个 spec，把 tickets 当任务图，跨 ready frontier 并行跑 implementer 子代理，最后 `/code-review` 收尾 | 一次性实现整份 spec |
| **wayfinder** | 把超出一个 agent 会话的大块工作规划成 issue tracker 上的决策票共享地图，逐个解决 | 超大工程分阶段导航 |
| **retro** | 会话后建议改进 agent 环境（导航/自动化检查/编码规范/steering 文件/工具），按严重度排序 | 编码会话结束后回顾 |

## 2. Model-invoked（模型或用户触发）

| 技能 | 作用 | 触发场景 |
|------|------|---------|
| **prototype** | 构建一次性原型回答设计问题（单一 HTML 文件或多种 UI 变体） | 探索设计问题 |
| **diagnosing-bugs** | 纪律化诊断循环：建反馈回路(变红)→最小化→假设→插桩→修复→回归测试 | 疑难 bug/性能回归 |
| **research** | 针对高信任原始来源调查问题，产出带引用的 Markdown，作为后台 agent 运行 | 研究性问题 |
| **tdd** | 测试驱动开发，红-绿-重构循环，一次一个垂直切片 | 开发功能/修 bug |
| **domain-modeling** | 主动构建打磨领域模型：挑战术语、边界场景、更新 GLOSSARY.md 和 ADR | 讨论代码术语/写 GLOSSARY/ADR |
| **codebase-design** | 设计 deep module 的共享纪律与词汇：小接口、干净 seam、经接口可测 | 设计/改进模块接口 |
| **code-review** | 对某固定点起 diff 做双轴审查：**Standards**（编码规范+Fowler 坏味道）与 **Spec**（是否忠实实现需求），并行子代理 | 审查分支/PR/WIP |
| **pr** | PR 正文的形状：最小可视化摘要 + 前后证据 + 合并风险判断（单向/双向门 + 爆炸半径） | 写 PR 正文 |
| **wizard** | 生成交互式 bash wizard，引导人类完成只能人做的步骤（配基础设施/设凭据/走第三方面板/一次性迁移） | 需要人类手动步骤 |

## 3. 主流程（Main Flow）

典型端到端链：`grill-with-docs → to-spec → to-tickets → implement(或 implement-spec) → code-review → retro`

- **grill-with-docs**：对齐 + 建共享语言。
- **to-spec**：沉淀成 spec。
- **to-tickets**：拆成工单。
- **implement / implement-spec**：实现（单工单 vs 整份 spec 并行）。
- **code-review**：双轴审查。
- **retro**：回顾环境改进。

## 4. 关键设计词

- **deep module**（codebase-design）：大量行为藏在小接口后，置于干净 seam，可经接口测试。Ousterhout 哲学。
- **tight feedback loop**（tdd/diagnosing-bugs）：反馈速度即速度上限。
- **tracer bullet**（to-tickets）：贯穿各阻塞边的可执行工单。
- **decision ticket**（wayfinder）：持有一个"问题"的子 Issue，其解决是决策而非构建切片。

## 5. 常见坑

1. **implement-spec 与 implement 混淆**：implement-spec 面向"整份 spec 一次并行实现"，implement 面向"单个 spec/ticket"。
2. **code-review 双轴漏一轴**：Standards 轴看"代码质量"，Spec 轴看"功能正确"，两轴并行、报告分开，防一轴掩盖另一轴。
3. **diagnosing-bugs 跳过反馈回路**：必须先建"能复现 bug 的反馈回路"，再最小化/假设/修复，否则盲目修。
4. **user-invoked 技能（setup-matt-pocock-skills 等）不能由其他技能调用**：前置条件需指导人类运行。
