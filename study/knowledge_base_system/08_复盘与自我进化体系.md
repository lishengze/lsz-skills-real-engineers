# 08 复盘与自我进化体系（Review & Self-Evolution System）

> 本仓库的 Agent 自我进化体系，位于 `task/` 和 `memory/`。从 otc_src 仓库迁移适配。

## 1. 体系文件清单

| 文件 | 作用 |
|------|------|
| `task/task_all.txt` | 工作准则（第 1~15 行）+ 成长体系思考 |
| `task/task_rule.md` | 通用工作规则（融合 task_all.txt + 自进化体系），跨会话/项目/场景 |
| `task/task_prompt.md` | 六大工作场景对话模板（学习文档/研究代码/开发测试/测试执行/代码答疑/问题分析） |
| `task/task_upgrade.md` | 自我进化体系完整方案（工作/学习/总结/知识库一体化） |
| `task/review/review_prepare.sh` | 复盘数据准备脚本（cron 驱动，半自动） |
| `task/review/README.md` | 复盘功能包跨项目复用说明 |
| `memory/self_evolution.md` | 记忆索引（跨会话自动加载，固化复盘机制+一句话触发指令） |
| `.chat/rules/project_rules.md` | 项目规则（面向所有 agent/会话，内容同 task_rule.md） |
| `work_log/` | 工作日志（复盘数据源，格式 YYYYMMDD.md） |

## 2. 核心思想

**一次任务，三份产出**：① 任务交付物；② 工作日志条目；③ 提炼后的知识条目。缺一不可。

## 3. 任务五阶段

```
阶段1 接单分类 → 阶段2 规划 → 阶段3 执行验证 → 阶段4 复查 → 阶段5 沉淀提交
```

- **阶段1**：判断编码/项目问答/通用问答/模糊任务。
- **阶段2**：复杂任务用 `add_tasks` 拆解；先检索记忆/知识库/历史排障。
- **阶段3**：改动前先读文件；必须验证；开发测试在 docker otc 容器内 + CMake 重新编译。
- **阶段4**：多轮复查直到某轮零修改；双轴审查（Standards + Spec）+ Fowler 12 种坏味道。
- **阶段5**：写工作日志 → 提炼知识 → 更新 Prompt.md → 询问用户是否提交 git → 关闭 docker。

## 4. 三层记忆模型

| 记忆层 | 类比 | 内容 | 位置 |
|--------|------|------|------|
| 工作记忆 | 短期 | 当前任务上下文 | 对话上下文 + add_tasks |
| 情景记忆 | 经历 | 每次任务流水 | work_log/YYYYMMDD.md |
| 语义记忆 | 知识 | 提炼的模式/坑点/规则 | memory/*.md + study/knowledge_base_system/ |
| 程序记忆 | 技能 | 标准流程/How-to | Prompt.md + 执行规范 |

## 5. 四级复盘体系

| 级别 | 频率 | 自动化程度 | 机制 |
|------|------|:---------:|------|
| 单任务即时复盘 | 每次任务后 | ✅ 全自动 | 内嵌于收尾自检清单 |
| 每日总结复盘 | 每日 | ⚠️ 半自动 | cron 备数据 + 用户触发 agent 反思 |
| 每周迭代复盘 | 每周 | ⚠️ 半自动 | 同上 |
| 每月能力升级复盘 | 每月 | ⚠️ 半自动 | 同上 |

**复盘核心五问**：
1. 本次任务是否完全达标？存在哪些瑕疵？
2. 哪些步骤高效、可固化复用？
3. 出现了哪些报错/卡点/低效问题？根因是什么？
4. 下次同类任务如何优化流程、规避问题？
5. 需要新增/优化哪些 Skill、知识库条目？

**复盘成果五转化**：高效经验→Skill/流程模板；报错踩坑→知识库；流程瑕疵→优化 SOP；能力短板→靶向学习；优质案例→标杆案例库。

## 6. 复盘自动化（半自动）

Agent 是被动响应式，无法自行唤醒。方案：
1. **cron 自动备数据**：`bash task/review/review_prepare.sh <daily|weekly|monthly>`
2. **用户一句话触发**：说"进行daily/weekly/monthly复盘"
3. **agent 执行反思**：读输入 → 核心五问 → 五转化 → 更新知识库+Prompt.md → 写报告

**一句话触发完整流程**（详见 `task/task_prompt.md §7`）：
```
第零步：主动运行 review_prepare.sh 刷新输入文件（防数据过时）
第一步：复盘核心五问
第二步：复盘成果五转化
第三步：更新知识库 + Prompt.md，写复盘报告
```

## 7. 工作日志规则

- 每完成一次工作记录一次（时间/内容/效果/经验教训，分块）。
- 不删除已有内容（只能追加，不能覆盖）。
- 文件名 `YYYYMMDD.md`，日期以系统 `date` 为准（非对话上下文日期）。
- 日期变更（过午夜）后新建文件，不追加到昨天文件。

## 8. 知识沉淀规则

- 知识库：`study/knowledge_base_system/`（系统级）+ `study/knowledge_base/`（业务级，本仓库暂无）。
- 知识生命周期：捕获 → 验证 → 提炼 → 索引 → 应用 → 保鲜。
- 禁止未经证实的猜测写进知识库；宁精勿滥。
- 跨会话知识迁移：通过 `Prompt.md` 被下一会话 Agent 重新加载。

## 9. 自检清单（任务收尾前核对）

- [ ] 任务交付物已完成并验证？
- [ ] 工作日志已记录到 `work_log/YYYYMMDD.md`（追加不覆盖）？
- [ ] 经验教训已提炼进知识库 + Prompt.md？
- [ ] 复盘后已核查经验教训融合进知识库（daily/weekly/monthly 必查）？
- [ ] 多轮复查直到某轮零修改？
- [ ] 已显式询问用户是否提交 git？
- [ ] docker 已关闭？

## 10. 常见坑

1. **工作日志日期用对话上下文日期**：对话上下文日期可能过时，必须用系统 `date` 命令的实际日期。
2. **复盘后经验未入知识库**：复盘后必须核查 knowledge_base_system/MEMORY.md/Prompt.md/memory 是否都融合了。
3. **提交时漏工作日志**：更新工作日志后应一起 git 提交，防止"提交后工作日志没提交"。
4. **review_prepare.sh 聚合边界（awk 章节匹配）**：经验教训段结束条件若只写 `/^## /`（二级标题），会把同级三级标题 `### 待验证假设/遗留问题/待办` 混入上一段；结束条件须同时匹配 `/^(## |### 待验证假设|### 遗留问题|### 待办)/`。"待验证假设"段起始匹配须行首锚定（`/^### .../`）。work_log 标题必须严格沿用 §11.1 模板，否则抓不到内容。
5. **复制复盘包到新项目要改示例路径**：review_prepare.sh 头部注释与 task_rule.md §8.4 中的 cron 示例是源项目绝对路径，复制后须替换为当前项目路径（脚本本体用 `dirname $0` 自适应，无需改代码）。
