# 10 系统排障与经验（System Troubleshooting & Lessons）

> 本仓库（daily_life 用途）在 Ubuntu NUC 上积累的系统排障经验，均为实测验证过的可复用结论。每次排障后沉淀到这里，避免重复排查。

## 1. UniCloud Workspace 云桌面黑屏（GStreamer 解码插件缺失）

**现象**：workspace-vdi（UniCloud 云桌面客户端，版本 E2004H07）打开后黑屏，远程桌面画面不显示。

**排障路径**（由浅入深）：
1. **连接层**：`/home/lsz/文档/Workspace/log/Workspace.log` 显示 `desktop is already connected success now`、VM `running` → 排除网络/认证问题。
2. **渲染层**：窗口树 `xwininfo -root -tree` 显示渲染子窗口 `StreamWin` 在 `-32000,-32000`（Qt 离屏隐藏位置，正常设计）。用 `xwd` 截图 + ImageMagick 分析 Vdp 窗口像素：全黑（`mean=0, unique_colors=1`）。
3. **进程层**：VdSession CPU 仅 3.3%（无解码渲染），但 `ss -tinp` 显示 fd 有 23MB 接收数据（`lastrcv:6`，视频流在传输）→ **收到但没解码**。
4. **解码层**：VdSession stderr（`/tmp/ws_start*.log`）出现 **GStreamer 管线崩溃**：
   ```
   gst_element_unlink: assertion 'GST_IS_ELEMENT (src)' failed
   gst_object_ref: assertion 'object != NULL' failed
   gst_bin_remove: assertion 'GST_IS_ELEMENT (element)' failed
   ```
5. **环境层**：`gst-inspect-1.0` 无 `avdec_h264`/`vaapih264dec` 解码器；系统只装了 `gstreamer1.0-plugins-good`，**缺 bad/ugly/libav**。

**根因**：客户端用 GStreamer 解码远程桌面 H.264 视频流，但系统缺少 GStreamer 视频解码插件，无法创建解码元素 → 解码管线崩溃 → 黑屏。

**解决方案**（三步，需按序）：
```bash
# 1. 安装 GStreamer 视频解码插件
sudo apt install gstreamer1.0-plugins-bad gstreamer1.0-plugins-ugly gstreamer1.0-libav gstreamer1.0-vaapi vainfo
# 2. 删除损坏的 GStreamer 注册表缓存（否则 avdec 解码器不注册）
rm -f ~/.cache/gstreamer-1.0/registry.*
# 3. 用干净环境重启客户端（避开 DevChat 注入的旧 libstdc++）
env -u LD_LIBRARY_PATH DISPLAY=:0 /userdata/UniCloud/Workspace/run.sh
```

**验证**：VdSession stderr 的 GStreamer-CRITICAL 错误消失；Vdp 窗口截图 `mean 0→0.95`、`颜色 1→106830`，画面正常。

**关键教训**：
- **Wayland/Xorg 不是云桌面黑屏的默认根因**。早期误判为"Wayland 渲染失败"，切 Xorg 后仍黑屏才转向解码层排查。黑屏要按"连接→渲染→进程→解码→环境"逐层排除。
- 云桌面客户端（VDP/SPICE 协议）通常用 GStreamer 解码，**缺解码插件是 Linux 上的高频黑屏原因**。
- StreamWin 在 `-32000,-32000` 是 Qt 离屏渲染窗口的隐藏位置，**属正常设计**，勿误判为 bug。

## 2. DevChat 扩展注入 LD_LIBRARY_PATH 干扰（旧 libstdc++）

**现象**：从终端/命令行启动 GUI 程序时，报 `libstdc++.so.6: version 'GLIBCXX_3.4.29' not found`，导致依赖 libstdc++ 的库（VAAPI 驱动 `iHD_drv_video.so`、GStreamer 插件等）加载失败。

**根因**：VS Code DevChat 扩展把自身路径注入 `LD_LIBRARY_PATH`：
```
LD_LIBRARY_PATH=/home/lsz/.vscode/extensions/gtht.devchat-*/platforms/linux-x64/_internal
```
该目录内的 `libstdc++.so.6` 是旧版，缺 `GLIBCXX_3.4.29`/`CXXABI_1.3.13`，被动态链接器优先加载。

**解决**：启动时清空 LD_LIBRARY_PATH：
```bash
env -u LD_LIBRARY_PATH <命令> ...
```
或用桌面快捷方式启动（不继承该环境变量）。

**排查技巧**：`ldd <lib>` 报 `GLIBCXX_3.4.29 not found` 时，先 `echo $LD_LIBRARY_PATH` 看是否被注入；用 `env -u LD_LIBRARY_PATH` 复测。

## 3. dpkg Installed-Size 单位异常导致虚报

**现象**：`dpkg-query -W -f='${Installed-Size} ${Package}\n'` 排序时，`workspace-vdi` 显示 1,313,714,176 KB（≈1.25TB），明显异常。

**根因**：dpkg 约定 `Installed-Size` 单位是 **KB**，但该包（UniCloud 云桌面）打包时把**字节数**填进了该字段，导致虚高 1024 倍。实际占用约 1.3GB（`du -sk /userdata/UniCloud/Workspace/` 实测）。

**排查技巧**：
- 对可疑大包，用 `du -sk` 实测真实占用，对比 dpkg 值。
- `Installed-Size` 值若 ≈ 实际字节数，说明打包方单位填错。
- 修正软件列表时，用实测值替换虚高值，并加备注说明。

## 4. Wayland 下云桌面渲染注意事项

- 云桌面/SPICE 类客户端依赖 X11+OpenGL 渲染，Wayland 下走 XWayland 兼容层，可能不稳定。
- 若 Xorg 会话可用（`/usr/share/xsessions/ubuntu-xorg.desktop`），可切换到 Xorg 提高兼容性。
- 切换方法：改 `/etc/gdm3/custom.conf` 的 `[daemon]` 段 `WaylandEnable=false`（有自动登录时无登录界面可选，需改配置）。备份原文件后再改。
- **注意**：Wayland 可能不是黑屏根因（见 §1），切换前先确认解码层是否正常。

## 6. Workspace 在 Ubuntu 24.04 登录即崩溃（捆绑旧 GnuTLS 与系统库符号冲突）

> 与 §1 黑屏（缺 GStreamer 解码插件）不同，本机 24.04.5 登录 Workspace 是**崩溃**（SIGSEGV），连接成功但很快断开、无法显示。

**现象**：Ubuntu 24.04.5 登录 Workspace（E2004H07）后报错、无法显示。日志显示连接流程正常（grpc 成功、认证 success），但 VdSession 崩溃。

**排障路径**：
1. **判定崩溃 vs 黑屏**：`/home/lsz/文档/dmp/*.dmp` 有 4 个 VdSession minidump，解析异常码均为 **SIGSEGV(0xb)@0x0**（空指针解引用）→ 是崩溃不是黑屏。
2. **定位崩溃线程**：协议日志 `/home/lsz/文档/VdSession/log/protocol-*.log` 显示崩溃线程在做 `spice_channel_connect_ws` 发起 `wss://` WebSocket 连接 → 崩溃在 SPICE websocket/TLS 连接。
3. **查库依赖**：`ldd libspice-client-glib-2.0.so.8.6.0` 报 `libgnutls.so.30: version 'GNUTLS_3_6_3'/'GNUTLS_3_7_4' not found`。
4. **对比捆绑 vs 系统库版本符号**：
   - 捆绑 `RUN/libgnutls.so.30` = **GnuTLS 3.5.18**，只提供 `GNUTLS_3_4`。
   - 系统 `libgnutls.so.30` = **3.8.3**，提供到 `GNUTLS_3_8_2`。
   - 系统 glib-networking 的 `libgiognutls.so` 需要 `GNUTLS_3_6_3`/`GNUTLS_3_7_4`。

**根因**：start.sh 把 RUN 目录放 `LD_LIBRARY_PATH` 首位，导致系统 `libgiognutls.so` 加载了 Workspace 捆绑的**旧 GnuTLS 3.5.18**，缺 `GNUTLS_3_7_4` 符号 → SPICE wss:// TLS 连接空指针崩溃。22.04 正常因 glib-networking 只需旧 GnuTLS 符号；24.04 需 3.7.4+ 故崩溃。

**⚠️ 修复不是简单重命名（第一次踩坑）**：重命名捆绑 libgnutls 让系统 GnuTLS 3.8.3 生效后，解决了 SIGSEGV，但 spice 客户端又报 `undefined symbol: gnutls_add_extension_string, version GNUTLS_3_4`（该函数是 H3C 定制，只存在于捆绑 GnuTLS 3.5.18 中，系统 GnuTLS 3.8.3 没有）。

**核心矛盾**（两个 GnuTLS 各缺对方所需符号）：
| 库 | 提供 | 缺失 |
|---|---|---|
| 捆绑 GnuTLS 3.5.18 | `gnutls_add_extension_string@GNUTLS_3_4`（H3C 定制，spice 需要） | GNUTLS_3_6_3/3_7_4（libgiognutls 需要） |
| 系统 GnuTLS 3.8.3 | GNUTLS_3_4~3_8_2（libgiognutls 需要） | `gnutls_add_extension_string`（spice 需要） |

**解决方案（两段式）**：
```bash
cd /userdata/UniCloud/Workspace/RUN
# ① 重命名捆绑旧 libgnutls，强制 libgiognutls 用系统 GnuTLS 3.8.3（解决 SIGSEGV）
mv libgnutls.so.30 libgnutls.so.30.bak
mv libgnutls.so.30.14.10 libgnutls.so.30.14.10.bak
# ② 编译 shim，通过 LD_PRELOAD 提供 gnutls_add_extension_string@GNUTLS_3_4（解决 symbol lookup error）
gcc -shared -fPIC libgnutls_h3c.c -o libgnutls_h3c.so -Wl,--version-script=libgnutls_h3c.map -ldl
# ③ 在 start.sh 加入 LD_PRELOAD
export LD_PRELOAD=/userdata/UniCloud/Workspace/RUN/libgnutls_h3c.so
```

**shim 原理**（`libgnutls_h3c.c` + `.map` 版本脚本）：
- 用 `__asm__(".symver gnutls_add_extension_string,gnutls_add_extension_string@GNUTLS_3_4")` 以非默认版本导出符号，匹配 spice 客户端的 `@GNUTLS_3_4` 引用。
- 实现内 `dlopen` 捆绑 GnuTLS `.bak`，`dlsym` 其真实函数并转发；解析失败兜底返回 0（spice 客户端把 0 当成功）。

**验证**：`readelf -sW libgnutls_h3c.so` 应显示 `gnutls_add_extension_string@GNUTLS_3_4`；`readelf -V` 应有 `GNUTLS_3_4` 版本节点。用 `.symver` 写测试程序调用该版本化符号验证。

**关键教训**：
- **升级系统后崩溃 ≠ 原系统黑屏**：先看崩溃转储/日志判定崩溃类型，不要照搬旧系统修复方案。
- **捆绑旧库与系统库版本符号冲突**是升级系统后高频崩溃源：`ldd <so>` 报 `version 'XXX' not found` = 运行时 LD_LIBRARY_PATH 优先加载了捆绑旧库；`undefined symbol: xxx, version V` = 用了系统新库但缺定制符号。
- **同一 soname 两个库各缺对方符号**时，用 LD_PRELOAD shim 补齐缺失符号（`.symver` 指定版本 + 转发到另一库实现）。
- **minidump 异常码**：SIGSEGV(0xb)@0x0 = 空指针；`undefined symbol` 是链接错误不是崩溃（无 minidump，进程直接退出，stderr 报 symbol lookup error）。
- **VdSession stderr 捕获**：进程 stderr 在 `/dev/null`，但 start.sh 后台输出 `/tmp/ws_restart*.log` 会捕获到 VdSession 的 symbol lookup error。

**minidump 快速解析（python）**：
```python
import struct
# 读 dmp 头拿 stream 目录，找 type=6(异常流)
# 异常码 0xb=SIGSEGV, 0xc0000005=ACCESS_VIOLATION
# 崩溃地址 0x0 = 空指针解引用
```

## 7. Workspace 24.04 登录后崩溃（恢复 quic/ 捆绑 glib 2.56 + libglib_h3c shim 补齐 glib 2.58+ 符号）

> 承接 §6。GnuTLS 问题解决后，登录仍崩溃（SIGSEGV 在 websocket 连接线程）。本次定位到 **glib 版本不匹配** 导致。

**现象**：GnuTLS shim 就位后仍崩溃。minidump 解析：异常码 `0xb`(SIGSEGV)，崩溃指令 RIP 落在 `libglib-2.0.so.0.8000.0`（**系统 glib 2.80**）偏移 `0x5be42`，`addr2line` 定位为 **`g_main_context_unref`**；崩溃线程栈回溯显示调用链来自 `libsoupquic-2.4.so.1.8.0` 与 `libglibquic.so`（quic/ 子目录的 H3C 定制 QUIC 库）。

**根因**：quic/ 子目录自带**捆绑 glib 2.56.0.4**，是 `libglibquic.so`/`libsoupquic.so` 编译所依赖的版本。但这些 glib 库（`libglib/gio/gobject/gmodule-2.0.so.0`）**被重命名成 `.bak` 禁用**（与 libgnutls 同一批操作），导致这两个 H3C 定制库加载了**系统 glib 2.80**。glib 2.56→2.80 的 `GMainContext` 内部结构不兼容，`libglibquic` 用旧 ABI 操作 → 内存损坏 → `g_main_context_unref` SIGSEGV。

**判定技巧**：
- 崩溃模块是**系统库**（`libglib-2.0.so.0.8000.0`）而非 H3C 库，说明是"别人用了不该用的系统库"。
- 用 `readelf -V` 确认 spice/libsoupquic/libglibquic/Workspace 对 glib 的引用**全部无版本化**（只有 GLIBC/SPICEGTK/GNUTLS 节点），故恢复捆绑 glib 2.56 不会引发符号版本冲突。
- 捆绑 glib 2.56 导出符号也**无版本化**（只有 GLIBC），能满足所有无版本引用。

**解决方案**：
```bash
cd /userdata/UniCloud/Workspace/RUN/quic
# 恢复被重命名禁用的捆绑 glib 2.56（连同 soname 软链）
mv libglib-2.0.so.0.5600.4.bak  libglib-2.0.so.0.5600.4 && mv libglib-2.0.so.0.bak  libglib-2.0.so.0
mv libgio-2.0.so.0.5600.4.bak   libgio-2.0.so.0.5600.4  && mv libgio-2.0.so.0.bak   libgio-2.0.so.0
mv libgobject-2.0.so.0.5600.4.bak libgobject-2.0.so.0.5600.4 && mv libgobject-2.0.so.0.bak libgobject-2.0.so.0
mv libgmodule-2.0.so.0.5600.4.bak libgmodule-2.0.so.0.5600.4 && mv libgmodule-2.0.so.0.bak libgmodule-2.0.so.0
```

**恢复后新问题**：系统库（`libatspi.so.0`、`libatk-bridge-2.0.so.0`、`libgtk-3.so.0`、`libproxy/.../libpxbackend`）需要 **glib 2.58+ 才引入的符号**，捆绑 glib 2.56 没有 → `symbol lookup error`。逐个报错：`g_once_init_leave_pointer`、`g_once_init_enter_pointer`、`g_string_free_and_steal`、`g_assertion_message_cmpint`、`g_mount_operation_set_is_tcrypt_*`、`g_mount_operation_set_pim`、`g_task_get_name`、`g_task_set_static_name`。

**解决**：编译 `libglib_h3c.so`（LD_PRELOAD shim）一次性补齐所有缺失符号（`libglib_h3c.c`）：
- 能转发的转发到捆绑 glib 2.56：`g_once_init_*_pointer`→`g_once_init_enter/leave`；`g_string_free_and_steal`→`g_string_free(s,FALSE)`；`g_assertion_message_cmpint`→`g_assertion_message`。
- 捆绑 glib 无对应功能的给空操作/兜底实现：`g_mount_operation_set_*`（TrueCrypt 属性，空操作）、`g_task_get_name`（返回 NULL）、`g_task_set_static_name`（空操作）。
- 编译：`gcc -shared -fPIC libglib_h3c.c -o libglib_h3c.so`。注意**不要用 glib 头文件类型**，`gboolean` 用 `typedef int`，避免依赖头文件。
- start.sh 的 LD_PRELOAD 追加：`export LD_PRELOAD=.../libglib_h3c.so:.../libgnutls_h3c.so`（冒号分隔多库）。

**一次性找全缺失符号的办法**（避免反复启动）：
```bash
# 合并捆绑 glib+gobject+gio+gmodule 的导出 g_ 符号
for f in libglib-2.0.so.0.5600.4 libgobject-2.0.so.0.5600.4 libgio-2.0.so.0.5600.4 libgmodule-2.0.so.0.5600.4; do
  nm -D --defined-only $f | awk '$3 ~ /^g_/ {sub(/@.*/,"",$3); print $3}'
done | sort -u > /tmp/bundled_glib_all.txt
# 找出系统库引用但捆绑 glib 缺失的无版本 g_ 符号
for so in /lib/x86_64-linux-gnu/libatspi.so.0 /usr/lib/x86_64-linux-gnu/libatk-bridge-2.0.so.0 /usr/lib/x86_64-linux-gnu/libatk-1.0.so.0 /usr/lib/x86_64-linux-gnu/libgtk-3.so.0; do
  [ -f "$so" ] && nm -D --undefined-only "$so" | awk '$2 ~ /^g_/ && $2 !~ /@/ {print $2}' | sort -u | while read s; do
    grep -qx "$s" /tmp/bundled_glib_all.txt || echo "$s"
  done
done | sort -u
```

**关键教训**：
- **恢复捆绑库前先确认"谁依赖它"**。quic/ 捆绑 glib 2.56 是 H3C QUIC 库的编译依赖，禁用后它们用系统 glib 2.80 崩溃。恢复捆绑库是正确方向，但要配套补齐系统库需要的 glib 2.58+ 符号。
- **minidump 解析要正确**：`MD_MODULE` 结构 108 字节，`module_name_rva` 在偏移 +20；模块名是 **UTF-16LE** 且前 4 字节是长度前缀（从 +4 开始解码）；`MD_CONTEXT_X86_64` 的 RIP 在偏移 **248**（不是 160）、RSP 在 152、RBP 在 160。寄存器读错会导致 RIP 看似不在任何模块。解析脚本见 `/home/lsz/code/workspacce_bug/parse_dmp.py`、`stack_walk.py`。
- **崩溃在系统库 = 有库误用了不该用的系统库**；崩溃在捆绑库 = 捆绑库自身问题。据此可快速缩小范围。
- **LD_PRELOAD shim 可补数据符号也可补函数符号**（本案例补的都是函数）。补数据符号用全局变量即可。

## 8. Workspace 24.04 黑屏（捆绑 GStreamer 1.14 解码链：旧 FFmpeg + libva-x11 符号缺失 + 注册表缓存）

> 承接 §7。登录连接正常后黑屏。与 §1（22.04 缺系统解码插件）不同，24.04 的 VdSession 用的是**捆绑 GStreamer 1.14**，装系统解码插件无效，需深入捆绑 GStreamer 解码链。

**现象**：登录连接成功（`isConnected=true`），画面黑屏。VdSession 日志反复报：
```
trying avdec_h264...
setDecBin: m_isSoftDec:true
GstPlayerBase::doPipeBuildManual m_decbin create failed   ← avdec_h264 元素创建失败
m_src:0x0
```

**排障路径**：
1. **先判用哪个 GStreamer**：`start.sh` 设 `GST_PLUGIN_PATH=.../RUN/gstreamer-1.0`，该目录是**捆绑 GStreamer 1.14.5**（`libgstreamer-1.0.so.0.1405.0`）。VdSession 用捆绑 GStreamer，**装系统插件无效**。验证：`LD_LIBRARY_PATH=...RUN... gst-inspect-1.0 avdec_h264` 报捆绑库符号缺失，说明加载的是捆绑库。
2. **捆绑 libav 插件依赖旧 FFmpeg**：`readelf -d gstreamer-1.0/libgstlibav.so` 显示需要 `libavcodec.so.57`/`libavformat.so.57`/`libavutil.so.55`/`libavfilter.so.6`。这些旧 FFmpeg 库**在 RUN 目录已有**（`libavcodec.so.57.107.100` 等），依赖完整（ldd 无 not found）。
3. **真正卡点 = 捆绑 libgstlibav.so 加载失败**：用 `env LD_LIBRARY_PATH=...python3 -c "import ctypes; ctypes.CDLL('.../libgstlibav.so', mode=os.RTLD_NOW|os.RTLD_GLOBAL)"` 复现报错：
   ```
   /userdata/UniCloud/Workspace/RUN/libva-x11.so.2: undefined symbol: va_fool_postp
   ```
4. **libva-x11 符号缺失**：RUN 目录有捆绑 `libva-x11.so.2.100.0`（需要 `va_fool_postp`，`objdump -T` 显示是**数据对象** `DO *UND*`），但 RUN 目录**没有核心 `libva.so.2`**，故用系统 `libva.so.2.2000.0`，而系统 libva **没有 `va_fool_postp`**。

**根因**：捆绑 `libgstvaapi.so`（GStreamer 插件）依赖捆绑 `libva-x11.so.2`，后者需要 `va_fool_postp`（数据符号），但提供它的捆绑 `libva.so.2` 缺失，回退到系统 libva 后无此符号 → 插件加载失败 → GStreamer 初始化异常 → `avdec_h264` 元素创建失败 → 黑屏。

**解决方案**（三步）：
```bash
cd /userdata/UniCloud/Workspace/RUN
# ① 禁用捆绑 libva-x11（重命名 .bak），让系统 libva-x11 2.2000.0 生效（与系统 libva 配套，无 va_fool_postp 需求）
mv libva-x11.so.2 libva-x11.so.2.bak && mv libva-x11.so libva-x11.so.bak && mv libva-x11.so.2.100.0 libva-x11.so.2.100.0.bak
# ② 删除 GStreamer 注册表缓存（关键！旧缓存里 libgstlibav 加载失败，无 avdec 元素）
rm -f ~/.cache/gstreamer-1.0/registry.*
# ③ 重启 Workspace（start.sh，保留所有 shim）
DISPLAY=:1 /userdata/UniCloud/Workspace/RUN/start.sh
```

**验证 avdec_h264 可用性**（用捆绑 GStreamer + 完整环境，含 LD_PRELOAD）：
```bash
env LD_LIBRARY_PATH=.../RUN:.../RUN/gstreamer-1.0:.../RUN/quic:.../RUN/'Device Redirect' \
GST_PLUGIN_PATH=.../RUN/gstreamer-1.0 \
LD_PRELOAD=.../libglib_h3c.so:.../libgnutls_h3c.so \
python3 -c "
import ctypes,os
GST=ctypes.CDLL('.../libgstreamer-1.0.so.0',mode=os.RTLD_GLOBAL)
GST.gst_init(ctypes.byref(ctypes.c_int(0)),None)
GST.gst_element_factory_make.restype=ctypes.c_void_p
GST.gst_element_factory_make.argtypes=[ctypes.c_char_p,ctypes.c_char_p]
print('avdec_h264:', 'OK' if GST.gst_element_factory_make(b'avdec_h264',None) else 'FAILED')
"
```

**关键教训**：
- **VdSession 用捆绑 GStreamer 1.14，不是系统的**。装系统 `gstreamer1.0-libav` 无效。先确认 `GST_PLUGIN_PATH` 指向哪套 GStreamer。
- **捆绑 GStreamer 解码链**：`libgstlibav.so`（用旧 FFmpeg `libavcodec57` 等，RUN 目录有）→ 依赖 `libgstvaapi.so` → 依赖捆绑 `libva-x11.so.2`（需 `va_fool_postp`）→ 捆绑 `libva.so.2` 核心缺失 → 系统 libva 无此符号。**逐层 ldd/readelf 依赖链**。
- **`undefined symbol` 是数据对象时**（`objdump -T` 显示 `DO *UND*`），说明缺的是全局变量/回调指针，不是函数。禁用不配套的捆绑库、改用系统配套库，比补符号更干净。
- **GStreamer 注册表缓存**（`~/.cache/gstreamer-1.0/registry.*`）会缓存"插件加载失败"的状态，修复底层后**必须删除缓存强制重扫**，否则元素仍不注册。
- **测试插件加载**：`ctypes.CDLL(..., mode=os.RTLD_NOW|os.RTLD_GLOBAL)` 能直接复现插件加载错误（比猜更准）；用 `env LD_LIBRARY_PATH=...` 而非在 python 里改 `os.environ`（后者进程启动后才改，动态链接器不认）。

**通用方法论**：
- **每次改动前先备份**：捆绑库重命名 `.bak` 即备份，可随时回退。
- **联动影响**：禁用/恢复一个捆绑库可能引发连锁符号问题（如恢复 glib 2.56 → 系统库缺 glib 2.58+ 符号）。每次改动后重启实测，用日志/报错驱动下一步。
- **复用 shim 模式**：凡是"同一 soname 两个库各缺对方符号"，用 LD_PRELOAD shim 补齐（§6 的 `.symver` 版本化符号、§7 的无版本函数符号）。
- **minidump/依赖链/插件加载**三类定位工具已沉淀：`parse_dmp.py`（异常+模块）、`stack_walk.py`（栈回溯）、`ctypes.CDLL`（插件加载复现）。
- **系统升级前做捆绑库兼容性体检（预防性，2026-10-14 复盘新增）**：升级系统（如 22.04→24.04）前，先对比捆绑第三方库（openssl/gnutls/glib/libva 等）与目标系统库的版本符号，提前发现潜在 `not found`/`undefined symbol` 冲突，而非升级后被动排障。体检命令：`readelf -V` 对比版本节点、`nm -D` 对比导出符号、`ldd` 检查运行时解析到哪套库。
